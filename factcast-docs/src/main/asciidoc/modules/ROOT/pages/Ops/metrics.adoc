= Metrics
:icons: font

Being a regular Spring Boot 2+ application, the FactCast Server uses https://micrometer.io[micrometer.io] as its metrics emitting/collecting solution.
In order to get started collecting the metrics FactCast Server emits, you'll need to choose a backend/store for your metrics.
Micrometer has https://micrometer.io/docs[lots of prebuilt bindings to choose from].
Please refer to the respective documentation in the **Setup** section of the micrometer docs.

When it comes to metrics, you'll have to know what you're looking for.
There are

- **Server** metrics in FactCast Server as well as
- **Client** metrics in the factcast client and additionally in the
- xref:ROOT:Usage/factus/metrics.adoc[factus client library].

We're focussing on _Server_ metrics here.

== Metric Namespaces and Their Organization

At the time of writing, there are six namespaces exposed:

- `factcast.server.timer`
- `factcast.server.meter`
- `factcast.store.timer`
- `factcast.ui.timer`
- `factcast.store.meter`
- `factcast.registry.timer`
- `factcast.registry.meter`

Depending on your micrometer binding, you may see a slightly different spelling in your data (like ' factcast_store_timer`, if your datasource has a special meaning for the '.'-character)

Furthermore, metrics in operations are automatically tagged with

- an operation name
- a store name ('pgsql' currently) and
- an exception tag ('None' if unset).

== Existing Metrics

There are a bunch of metrics already emitted in the server.
These metrics can be grouped by type:

- Timers (collecting durations of code execution)
- Meters (collecting metric events, for example, occurrences of errors)

As this list is continuously growing, we cannot guarantee the documentation's completeness.
If you want to see the current list of operations, please look at https://github.com/factcast/factcast/blob/main/factcast-store/src/main/java/org/factcast/store/internal/StoreMetrics.java[StoreMetrics.java]
, https://github.com/factcast/factcast/blob/main/factcast-store/src/main/java/org/factcast/store/registry/metrics/RegistryMetrics.java[RegistryMetrics.java]

=== Measuring publication throughput

The following operations use the existing `store=pgsql` tag. Timers belong to
`factcast.store.timer`; counters and distribution summaries belong to `factcast.store.meter`.
Durations use a monotonic clock and are exported in the backend's timer units.
These measurements do not change flush scheduling or the default flush delay of zero.

[cols="1,1,3",options="header"]
|===
|Operation |Type |Meaning
|publicationBatchEntries |Distribution summary |Number of API publications drained into each queue batch. One list of facts is one publication.
|publicationBatchFacts |Distribution summary |Total facts in each drained batch. Failed batches are included; individual fallback attempts do not add batch-size samples.
|publicationQueueWait |Timer |Enqueue until removal from the queue, once per publication. Includes scheduling delay and waiting behind earlier batches; excludes its database execution and fallback retries.
|publicationBacklogIdle |Timer |Time with queued work while no flush is active, once per productive flush. Starts at the first enqueue into an idle, empty queue, or when the previous flush finishes with entries remaining. Excludes active flush work (including fallback and completion callbacks) and time when the queue is empty. Zero durations are included; no-op scheduled tasks add no samples.
|publicationTransaction |Timer |One `doPublish` attempt, around `TransactionTemplate.execute`: includes connection acquisition, lock acquisition, inserts, and transaction completion. Failed combined attempts and individual fallback attempts are all recorded, with the exception class in the `exception` tag. When joining a caller transaction, this measures only the participating call, not the caller's eventual commit or rollback.
|publicationLock |Timer |The lock-acquisition call inside `doPublish`, including lock waiting and call overhead. Already-held locks can return immediately. This does not measure how long the lock is held or the earlier conditional-publication validation lock.
|queuedPublicationsCommitted |Counter |Successfully committed queued API publications, incremented after `doPublish` returns and before completing the caller's future. Failed attempts do not increment it.
|queuedFactsCommitted |Counter |Facts belonging to those committed queued publications. Use its rate for successful queued facts per second.
|publicationBatchFallback |Counter |Combined queue batches that failed and entered individual retries.
|===

Queue measurements and committed counters cover only calls routed through `PublicationQueue`.
Calls participating in a caller transaction bypass that queue. Transaction and lock timers also
cover direct publications, so use a workload consisting only of queued unconditional publications
when comparing those timers with queue metrics. `exception=None` means an attempt returned
normally; it does not imply that a surrounding caller transaction has committed.

For a baseline, use 256 concurrent synchronous producers, fixed payload/list sizes and batch limit,
a warm-up period, and a fixed measurement window. Start without duplicates. Repeat runs with
`factcast.store.publish-batched.flush-delay-millis` set to 0 and the delays being evaluated,
alternating their order and keeping database conditions comparable.

Compare successful facts/sec and publications/sec (counter rates), batch size distributions,
queue-wait and backlog-idle durations, and transaction/lock durations. For summaries, sum divided
by count gives mean batch size; timer total duration divided by count gives mean duration.
Backend percentile or histogram configuration is needed for p50/p95/p99; this instrumentation
does not enable histograms automatically. Record end-to-end publish latency at the producer as
well, since store timers exclude network and client overhead. Treat any throughput difference
smaller than run-to-run variation cautiously, including the overhead of collecting metrics.

* Unchanged batch sizes with higher queue wait indicate that the flush delay adds waiting without improving batching.
* Larger batches with lower throughput indicate that batching savings do not compensate for idle time.
* Material backlog idle time at delay zero suggests that continuously draining the queue could improve throughput.
* Long transaction durations with little backlog idle time suggest investigating database work; compare lock acquisition time to distinguish contention.

Once the baseline is understood, introduce a controlled duplicate rate and inspect
`publicationBatchFallback`. Committed counters exclude rolled-back facts, while transaction timers
include the cost of failures and retries. SQL statement consolidation and preserving batching during
failure recovery are separate follow-up experiments; neither is changed by this instrumentation.

=== gRPC Metrics

If you're looking for remote calls and their execution times (including marshalling/de-marshalling from protobuf), you can have a look at the metrics automatically added by the https://yidongnan.github.io/grpc-spring-boot-starter/en/[gRPC library]
that we use.
The relevant namespaces are:

- `grpcServerRequestsReceived` and
- `grpcServerResponsesSent`

These automatically added metrics only focus on service methods defined in the https://github.com/factcast/factcast/blob/main/factcast-grpc-api/src/main/proto/FactStore.proto[protocol buffer specs].
Since a gRPC remote call triggers not everything we want to measure, we introduced additional metrics.
When comparing, for instance, the automatically added durations of gRPC vs. the 'factcast.store.duration', you will find a subtle difference.
The reason for this is that instead of including the gRPC overhead, we chose to only measure the actual invocations on the FactStore/TokenStore implementation.
Depending on your needs, you may want to focus on one or the other.

=== Executor Metrics

Micrometer provides an integration to monitor the default thread pool executor created by Spring Boot.
Under the same namespace `executor.*`, we publish metrics for our own thread pool executors used inside FactCast.

You can distinguish them by the `name` tag.
Currently, these are:

- `subscription-factory` - used for incoming new subscriptions
- `parallel-transformation` - used for batch transformation of buffered facts
- `paged-catchup` - used for buffered transformation while using the paged catchup strategy
- `transformation-cache` - used for inserting/updating entries in the transformation cache (only if you use persisted cache)
- `pg-listener` - used by the Guava EventBus that receives signals from the PostgreSQL
- `telemetry` - used by the Guava EventBus that receives signals from the FactCast Server ( see xref:ROOT:Ops/telemetry.adoc[telemetry])

See https://micrometer.io/docs/ref/jvm for more information.

=== UI Metrics

Special metrics for the FactCast-Server UI are published via `factcast.ui.timer` namespace.

[cols="1,1,2",options="header"]
|===
|Operation |Type |Description
|plugin-execution |`timer` |Time to execute a specific plugin for one fact.
|fact-processing |`timer` |Overall time to process one fact. This includes execution of every plugin, parsing JSON payload and building the final representation model.
|===

Additionally, all methods of the `org.factcast.server.ui.adapter.FactRepositoryImpl` are measured time-wise, and can be visualized via `class` and `method`
dimension.
